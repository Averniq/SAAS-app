# Staff Management backend contract and rollout boundary

This is a local-only migration candidate. It has not been applied to either Production backend. The complete SQL is the original `supabase/migrations/20261018044445_staff_management.sql` followed by append-only `supabase/migrations/20261018092519_staff_invitation_transport_boundary.sql`. The latter supersedes the original invitation transport contracts.

## Additive state

`restaurant_staff` receives `display_name`, `is_active`, `version` and `updated_at`. Existing identities, roles, keys, associations and active access remain unchanged. Empty display names are permitted for existing records only; the edit RPC requires a trimmed name of 1â€“100 characters. `restaurant_invites` receives display name, request UUID and reservation timestamp. The new append-only `staff_management_audit` stores tenant, actor, target, action and safe before/after state. It stores no password, JWT, invite bearer or email-link token. Membership and audit writes remain RPC-only; active tenant Owners can read audit records through RLS.

## Authoritative access

`is_restaurant_staff` and `has_restaurant_role` consult current `is_active`, never JWT role metadata. `can_manage_restaurant_staff` preserves existing platform-admin and active Owner/Manager invitation rights. All existing RLS users of these helpers therefore enforce suspension. Kitchen `update_restaurant_order_status` and financial `record_authoritative_payment` / `list_authoritative_payment_operations` have direct role reads and are explicitly redefined to require active membership. Public canonical QR APIs remain token-scoped and unchanged; retired legacy public ordering entrypoints remain ungranted. The initial Owner bootstrap is service-only, create-once and rejects any existing membership, including disabled memberships. No global Auth ban or password change is used for suspension, so the same Auth identity can retain access to another restaurant.

## RPC contracts

- `update_restaurant_staff(uuid,uuid,text,text,boolean,bigint)` accepts tenant, membership, name, role, active and expected version. Only a current active tenant Owner may mutate. Owner or self targets are immutable. Only Manager, Staff, Kitchen and Cashier are accepted. Returns the exact persisted membership identity, tenant/user IDs, safe editable state and incremented version.
- `reserve_staff_invitation_for_delivery(uuid,uuid,text,text,text,uuid)` is executable only by `service_role`. The Edge endpoint verifies the caller through Auth `/user` and supplies that verified actor ID using a private server-runtime credential. SQL independently locks and checks the actor's current active Owner/Manager membership (or existing platform-admin authority), tenant and non-Owner role allowlist. Returns reservation material only to the server endpoint. The browser never receives it. Identical actor/payload/request UUID returns `delivery_required=false`; changed actor/payload is rejected. Tenant/email cooldown is 60 seconds; a new successful reservation invalidates the earlier invite.
- Retired `create_staff_invitation` and `create_restaurant_invite` signatures are retained as fail-closed stubs, with execution revoked from browser and service roles. They cannot create invitations or return tokens. The old private Owner-capable reserve helper is dropped. Managers retain email invitation, listing and revocation through the approved UI/endpoint.
- `accept_restaurant_invite(uuid)` requires an authenticated recipient whose actual Auth email is confirmed and exactly matches the normalized invitation email. It consumes only pending, non-expired invitations. Existing active membership role and identity are preserved; disabled memberships are rejected. Accepted/revoked replay fails. It rejects Owner/unknown invitation roles, including preexisting Owner invitations, and never changes the restaurant Owner pointer. It never trusts URL roles or user metadata. It returns tenant/slug/name and the actual membership role.
- `revoke_restaurant_invite(uuid)` retains Owner/Manager/platform behavior and audits successful revocation.
- `list_restaurant_team(uuid)` retains existing fields and adds member id/display_name/is_active/version and invite display_name. Invitation entries omit token/link/URL fields. Disabled callers cannot list the tenant.

## Concurrency and isolation

Every invitation/membership mutation takes the same transaction-scoped advisory lock keyed by restaurant before locking the actor, target or invitation. This serializes accept/revoke/create/edit, prevents lock-order inversions between those paths and ensures a stale invite cannot race a membership role/status edit. Current actor and target state are then read under row locks. `version` makes simultaneous stale edits fail, not overwrite each other. Role/status edits revoke pending invitations for the target's current email and invitations issued by that member in the same transaction. Acceptance also rechecks the original inviter's current authority, so stale invitations cannot outlive a suspension/demotion. Tenant input is never enough to authorize a write: actor membership, target membership and restaurant are all matched. The advisory lock uses a 64-bit hash; a collision can only serialize unrelated tenants, not grant access.

## Migration, deployment and recovery

Each migration is transactional. Apply BOTH in timestamp order before exposing the new endpoint/frontend. New staff-management/invitation SECURITY DEFINER functions pin an empty search path and qualify referenced objects. Existing Kitchen/payment replacements retain their reviewed fixed public/extensions/pg_temp paths. Private helpers are in an unexposed schema and client execution is revoked. The sole exposed reservation wrapper grants execution only to service_role; authenticated clients retain only authorized team/edit/accept/revoke operations. Direct membership writes remain revoked. No new privileged credential enters frontend build configuration.

Production application requires separate explicit approval after catalog/RLS review. Deploy approved backend migration and email endpoint before the frontend. Review Auth email redirect allowlist, transport and endpoint origin settings separately; no Production configuration change is implicit in this PR. Validate with designated synthetic accounts/tenant. Retain existing data and audit.

There is no destructive down migration. A frontend rollback must leave backend suspension checks in place, or disabled members could regain access. Recover through an explicitly reviewed forward patch; do not drop active flags, audit records, invitation invalidation or authorization checks. No schema/data reset, membership replacement, QR operation or historical order rewrite is needed.
