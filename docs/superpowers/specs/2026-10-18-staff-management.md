# Staff Management MVP — approved design and security contract

Base: c7adb471b4f81b310a72e37b3b5167043ebd79ff. Product scope approved 2026-10-18; implementation and migrations are LOCAL ONLY. Production migration/deployment require separate approval.

## Scope and decisions
Extend Restaurant Team in Admin. Owner can edit non-owner display names, roles (manager/staff/kitchen/cashier) and active status. No owner modifications, self-disable, Auth email edits, deletion or global ban. Manager retains existing invite/list/revoke and operational rights, but cannot edit existing memberships. Preserve all IDs, QR and history.

Invitation-first provisioning uses a narrow Supabase Edge function to reserve a tenant invite via caller-JWT RPC, then request a Supabase Auth email one-time sign-in link with account creation enabled. Supabase Auth creates a missing identity or reuses an existing identity; no owner-selected passwords, admin listUsers lookup, service-role credential or custom SMTP is necessary. Link goes to allowlisted /join/<invite-token>. It authenticates the recipient; invitation acceptance remains a separate atomic, email-matched database operation. Recipient may explicitly set their own password in the authenticated invitation completion screen, or retain their existing password. Normal account password setup is separate from recovery; existing recovery PKCE provenance/resend code must not be relaxed. Do not attempt Owner-browser PKCE for a recipient email link. Verify the Auth session against /user before consuming invite credentials; never trust URL role/email/tenant fields. Never log link tokens, passwords or JWTs.

## SQL/API contract
- restaurant_staff: display_name text default '', is_active boolean default true, version bigint default 1, updated_at timestamp. Existing records stay active and all identities unchanged.
- restaurant_invites: display_name text default ''; accepted membership/version guard as needed; resend reservation and delivery state to bound rate limiting and idempotency.
- staff_management_audit: tenant, actor, membership/invite, action, before/after safe fields, timestamp. No password/token/email-link material. Tenant Owner read, RPC-only insert.
- update_restaurant_staff(p_restaurant_id uuid,p_membership_id uuid,p_display_name text,p_role text,p_is_active boolean,p_expected_version bigint) returns {id,user_id,restaurant_id,display_name,role,is_active,version}. Owner actor must currently be active; lock actor/target consistently, reject owner/self target, cross-tenant IDs, blanks/unknown roles and stale version. Audit atomically. Role/status change revokes pending invites for target email. No direct membership write grants.
- create_staff_invitation(p_restaurant_id uuid,p_email text,p_role text,p_display_name text,p_request_id uuid) returns {id,token,email,role,expires_at,display_name,delivery_required}. Active Owner/Manager (and existing platform admin policy) authorization; Manager cannot invite Owner; MVP endpoint restricts all invite roles to non-owner. Shared tenant/email 60-second resend cooldown and request-id idempotency in DB. Deny invites that would change existing active/disabled membership. Legacy create_restaurant_invite keeps its signature and delegates to hardened logic; retain existing Owner-invite behavior only on legacy path.
- accept_restaurant_invite(p_token uuid): verified email, non-expired pending invite, lock consistently; create membership only if absent, preserve existing role/identity, reject disabled membership; no stale invite may restore privilege. Accepted/revoked replay fails closed.
- list_restaurant_team retains existing fields plus membership id/display_name/is_active/version and invite display_name. Restrict suspended callers.
- Every protected role reader, helper, RLS and exposed RPC must consult current active membership, including payment/Kitchen/bootstrap and older direct-role functions. Public token-only QR operations remain unaffected. Own membership SELECT can expose own disabled status but cannot grant restaurant data.

## Frontend contracts
Client updateRestaurantStaff(restaurantId,membershipId,{displayName,role,isActive,expectedVersion}), sendStaffInvitation(restaurantId,{email,role,displayName,requestId}); function endpoint staff-invite. Reuse listRestaurantTeam/revoke/accept. getMemberships filters is_active; version/auth/tenant fence async staff UI. Name length 1..100 after trim. Email/login identifiers read-only for existing members. Server confirmation before UI update, pending duplicate clicks disabled, clear errors and no raw internal identifiers. Disabled list separate, confirm status changes. Owner rows read-only. Retain Manager legacy invite/list/revoke view. Authenticated invitation password setup is a distinct own-account adapter, validated via /user, and never grants recovery authority.

## Acceptance and safety
Use disposable Docker Supabase, synthetic multi-tenant Auth identities and local email capture only. Test new/existing identity invitations, role/status edits, shared identity across tenants, retained valid JWT denial across all protected reads/RPCs, stale/revoked/expired/email-mismatch invites, Owner/Manager/Staff boundaries, update races, resend/idempotency, history/QR preservation. Browser 375/768/1280 for Owner, Manager, Staff, errors/loading/empty/repeated actions and invitation setup. Run existing routing/recovery/QR/payment/Kitchen/table-rename regressions, build and credential scan. Independent security review required. Draft PR only. No Production connections, migrations, data, roles, DNS, Netlify or QR operations.

## Rollback/release boundary
Forward-only additive migration, preserve disabled flags/audit on rollback. Never roll authorization helpers back to ignore disabled status. Frontend rollback must leave backend suspension checks deployed. No automatic DROP/data restoration. Production deployment plan must include migration/catalog review and explicit approval, then backend before frontend, server email redirect allowlist review, verification with designated synthetic tenant and recovery by reviewed forward patch. Full SQL supplied by migration files, not applied to hosted projects.
