# Staff Management deployment and recovery plan

This PR is a review candidate only. The final review read Production catalog metadata only (no application/Auth rows or token values); it matched the approved baseline. No hosted Supabase project has been modified. No function/frontend deployment, Netlify change, migration application or Production staff operation has been performed.

## Complete SQL and compatibility

Review BOTH complete append-only migrations `supabase/migrations/20261018044445_staff_management.sql` and `supabase/migrations/20261018092519_staff_invitation_transport_boundary.sql`, plus `docs/staff-management-backend.md` for the RPC/RLS matrix and `docs/staff-management-security-review.md` for independent review. It adds membership display name/active/version/update time, invitation reservation fields and an audit table; replaces authoritative membership helpers, hardened invitation RPCs, and direct Kitchen/payment role readers. Existing memberships default active. Existing IDs, historical associations, orders and QR hashes are preserved. No existing migration file, pinned Auth SDK, dependency lockfile, service worker or Netlify configuration is changed. Runtime requirements include function-only public origin/key settings, a private Edge-only service-role JWT credential, and separately reviewed Auth redirect support. Never add the server credential to frontend or Netlify public build configuration.

2. Under that later approval, capture read-only Production schema/function/ACL/RLS definitions. Compare every replaced signature/body and grant to the approved baseline; stop for catalog drift. 3. Rehearse the migration and API tests in an isolated non-production environment. Confirm migration transaction atomicity and backup/recovery posture. Preserve all active/disabled membership state and audit data.
4. Apply BOTH approved database migrations in timestamp order before exposing the new endpoint/frontend. Schedule a controlled invitation maintenance window: old frontend direct invitation creation will fail closed once the follow-up migration retires that RPC, until the new email endpoint/UI are available. The handler fails closed without a suitable server credential. It verifies the caller via Auth /user, supplies only that verified actor ID to the server-only reservation RPC, and SQL rechecks current tenant authority. Auth OTP uses the public key; no custom SMTP secret or Auth-admin provisioning operation is used. Keep default gateway JWT verification enabled. Do not mutate real customer staff/accounts as a smoke test. Stop if any gate fails.

## Recovery

Before publication, stop with the existing release unchanged if any gate fails. Never restore retired token-returning RPC grants, legacy Owner invitation creation or token-bearing team listings. For email transport trouble, stop new invitations or disable the endpoint/UI; preserve pending reservations because delivery may have occurred. Resend is shared-cooldown gated and a repeated request ID never sends twice.

After backend migration, never revert active-membership checks to their old definitions: that would re-enable disabled access. A frontend rollback may hide the new controls, but must leave suspension enforcement, invalidated invitations and audit records intact. Use a reviewed forward patch for backend defects; do not drop columns/audit, reset data, globally ban/delete Auth users, replace membership IDs or rewrite historical records. Do not automatically reactivate members or replay accepted invitations. Any Production recovery action needs explicit approval.

## Verification boundary

Browser screenshots use synthetic localhost fixtures. Database/API tests use actual disposable local Docker Postgres, GoTrue and PostgREST. SMTP integration captures actual local email and consumes real local Auth links; it invokes the same endpoint handler under Node. The Deno wrapper is packaged offline using the installed Supabase Edge runtime image with network disabled. A hosted Edge deployment and live email-provider acceptance have deliberately not been performed; these are later deployment gates, not claims made by this Draft PR.

Recheck catalog drift immediately before any separately approved hosted migration. This comparison does not grant migration or deployment approval, verify hosted gateway/email delivery, or modify Production.
