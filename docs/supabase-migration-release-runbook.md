# Supabase migration release gate

Status: **blocked as of 2026-08-12**. This runbook is deliberately conservative: it does not provide a way to repair or push a hosted migration ledger.

## Versioning policy

Legacy three-digit migrations are immutable evidence. Every new migration must be created with `supabase migration new <description>` and retain the unique 14-digit UTC version generated by the CLI. Do not rename, renumber, squash, or edit legacy files. A correction to an already-applied migration is a new timestamped forward migration only.

## Required evidence before approval

1. Capture migration ledgers read-only from local, staging, and hosted environments. For duplicate legacy versions, prove object effects through catalog inspection rather than matching ledger version text.
2. Capture a catalog manifest for each environment, including relations, columns/defaults, constraints, indexes, views, triggers, functions/signatures, definer mode/search path/EXECUTE ACLs, grants, RLS state/policies, extensions, and storage policies.
3. Review the source and exact hosted definition of `public.get_public_tenant_context(text)` and its `tenant_domains` dependency. Do not invent or copy an unreviewed definition into a migration.
4. Reconcile the deployed historical `011` blob. Preserve its working-tree policy-drop intent only in a new timestamped migration after the deployed variant is proven; do not edit `011`.
5. Resolve the two `022` effects with unique forward identities after proving both effects in every environment. Do not rename either historical file.

## Isolated replay procedure

Only after the inventory and catalog manifest have been explicitly approved:

```powershell
supabase --version
supabase start
supabase db reset --local --no-seed
supabase migration list --local
supabase db lint --local --level warning
node scripts/test-migration-release-gate.mjs
```

Use no `--linked`, `--db-url`, `db push`, or `migration repair` command in this procedure. Compare the rebuilt catalog to the approved local, staging, and hosted manifests before proposing any environment-specific repair plan.

## Required release assertions

The gate must reject a changed frozen hash, unknown or untracked historical migration, malformed or duplicate version, empty migration, inventory drift, missing required catalog section, missing public tenant function, changed RLS/grants/function metadata, or failed clean replay. It must also assert the reporting exclusion and staff-presence outcomes formerly sharing `022`.
